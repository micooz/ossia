## 1. 交付范围

MVP 覆盖四条链路的桌面版：导入（MusicXML / MIDI）→ SVG 渲染 → 点击定位 →
自然语言修改（5 道闸门）→ before/after 对比 → 接受/还原 → 版本历史 → PDF / MIDI 导出。

| 包 | 形态 | 职责 |
|---|---|---|
| `packages/backend` | Next.js 16（仅 `app/api/**` + `app/health`） | 服务端五服务 A–E；未来兼作官网渲染 |
| `packages/ui` | Vite + React 19 静态 SPA | 跨端 UI（不含任何 Node / Tauri 依赖） |
| `packages/desktop` | Tauri 2 | macOS 外壳：开窗 + 注入 API 地址与 token，不启动任何子进程 |
| `packages/ly` | 纯 TS | L0/L1/L2 索引、SMF 解析、音高状态机 |
| `vendor/` | 锁文件 + 解压产物 | 仅 LilyPond 2.26.0（gitignored，由 `vendor/ENGINE.lock` 复现） |

## 2. 与计划的偏差（实现层，逐条）

| # | 偏差 | 原因（实测） |
|---|---|---|
| 1 | 渲染分两趟，不用 `--midi` | LilyPond 没有 `--midi` 选项：MIDI 只在源码含活动 `\midi{}` 时才产出；且 `--svg` 不出 PDF。SVG 趟 + PDF/MIDI 趟，门禁另用 0.5 s 的 MIDI-only 趟 |
| 2 | 渲染文本替换为 `\pointAndClickOn`，落库源码保持原样 | `musicxml2ly` 默认写 `\pointAndClickOff`，而 L3 锚点是定位链路的前提。替换只在派生文本上做，且保持行数不变（否则 SVG 锚点行号不再指向落库源码） |
| 3 | SVG 在入库前清洗，而非出口时 | 锚点 href 带本次 scratch 目录绝对路径；不清洗则同一 `.ly` 每次渲染算出不同 asset hash，缓存失效（实测清洗后哈希稳定） |
| 4 | 新增 `packages/app/src/server/layout-join.ts` | 「system s 的第 k 列」与「声部的第 m 小节」不能假设等价。该模块实测全局小节号 = 跨页 running column index + 1，并以此把点击列转成全局小节 |
| 5 | 导入闸门三态 `clean / needs-confirmation / refused` | `Negative skip` 属于时间线压缩，§3.11 结论 1 明确不可人工确认放行，故 `confirm=all` 也拒绝（实测 422 `needs-review`）；局部损失走 `confirm=<digest>` |
| 6 | dev 端口默认 3210（非 3000） | 3000 是用户 Maisow `next dev` 的常驻端口，不占用 |
| 7 | CORS 预检放在 `src/middleware.ts` | Next 在路由模块之前应答 OPTIONS，`withApi` 的 OPTIONS 分支永远到不了，浏览器只看到无头 204 |
| 8 | head 判定 = tip node（`max(seq)`），不比较内容 hash | 还原会复用旧内容 hash，按 hash 比较会同时出现两个 head |
| 9 | PDF 不做可复现哈希 | 同一源码两次渲染（`pdf1/out.pdf`、`pdf2/out.pdf`）sha256 不同：LilyPond 写入 `CreationDate`/`ModDate`。SVG/MIDI 走内容哈希缓存，PDF 只作为导出件 |
| 10 | MusicXML 补丁回放（导出）不在 MVP | ADR-0003 尚未撰写，导出格式只有 `pdf` / `midi` |

## 3. 构建期发现并修复的缺陷（每条含测量）

### 3.1 `fs.cpSync({dereference:true})` 不解引用（致命）〔历史：sidecar 打包链路，2026-10-10 已随该链路整体删除〕

`next build` 的 standalone 树内部有 29 个相对软链（实测：0 绝对、0 断裂），
本身自洽。用 `cpSync({dereference:true})` 复制时它**不解引用**，反而把相对链接改写为指回
`packages/app/.next/standalone` 的绝对路径：本地能跑，一旦 `.next` 被清理或进入 `.app` 立刻
`Cannot find module 'next'`，sidecar 在包内直接死亡。

修复：`cp -R -L`，随后 `hoistStore()` 把 `.pnpm` 目录压平成 `packages/app/node_modules`，
再删除 111 MB 的 store 副本。构建脚本现在硬性断言 0 软链 + 必要文件存在 + 冒烟测试
（真的用复制出来的 node 启动 server 并打 `/health` 与带 token 的 `/documents`）。

### 3.2 Tauri `bundle.resources` 静默丢弃软链（致命）〔历史：`bundle.resources` 配置块已于 2026-10-10 删除〕

实测 29 个软链进、0 个出。与 3.1 叠加后表现为「构建成功、运行即崩」。数组形式的 resources
还会把内容嵌到 `Contents/Resources/resources/` 下。修复：改用对象形式显式映射
（`"resources/sidecar/node": "sidecar/node"` 等），并在打包后断言
`Contents/Resources` 软链数为 0（当前实测 0）。

### 3.3 `tauri build` 不刷新 resources（打包陈旧代码，致命）〔历史：`prepare.mjs` 与 `src-tauri/resources/` 已于 2026-10-10 删除；同类风险现由 §7 的 `pnpm dev:desktop` 说明替代〕

`bundle.resources` 只做复制，**不会**重建 `src-tauri/resources/`。因此改完服务端代码后
`tauri build` 产出的 `.app` 仍内含上一次构建的字节。实测方式：在包内
`.next/server/chunks/*.js` 中直接搜到缺陷 3.4 的旧替换串。

修复：`build.beforeBuildCommand = "node scripts/prepare.mjs build"`，该脚本重建 standalone、
重建 SPA dist，再 materialise `src-tauri/resources/{sidecar,engine}`。现在 `tauri build` 是
自洽可复现的（实测 `runtime.json.builtAt` 随构建更新）。

### 3.4 `\pointAndClickOn` 少写一个反斜杠（致命，仅 MIDI 导入触发）

JS 字符串里 `'$1$2 \pointAndClickOn$3'` 的 `\p` 被转义吃掉，实际生成
`\version "2.14.0" pointAndClickOn`，渲染报
`score.ly:4:1: error: syntax error, unexpected \layout, expecting '.' or '='`。

`musicxml2ly` 的输出自带 `\pointAndClickOff`，走的是另一分支，所以 MusicXML 链路从未暴露此缺陷；
**只有 `midi2ly` 导入（无 `\pointAndClickOff`）会 100% 渲染失败**。修复后包内 chunk 实测为
`'$1$2 \\pointAndClickOn$3'`，MIDI 导入渲染 2 页 / 8 system 通过。回归固化为
`packages/app/scripts/verify-render.ts`（17 项）。

### 3.5 模型输出 `\f` 变成 U+000C 写进用户源码

力度类指令让模型返回 `\f`，JSON 解析后是控制字符 U+000C（form feed），落库后
`G-e` 的 token 差分显示 `+[\x0c]`。LilyPond 恰好容忍它，所以渲染看不出异常——
属于「静默污染用户文件」。修复：`agent.ts::sanitize` 增加 `repairControls`，
`\x0c`→`\f`、tab→两空格、其余 C0 丢弃（`\f` 是唯一转义为控制字符的 LilyPond 命令）。
实测：包内服务端跑完整链路后，CAS 中所有 `.ly` 无 C0 字节且候选含 `\f`（`verify:flow` 全绿）。
回归固化为 `verify-agent.ts`（15 项）。

### 3.5c 接受修改后，谱面仍显示修改前的版本（UI 缺陷）

`CompareView` 的 `onDecided` 回调把 `doc.document`（**决策前**的快照）的 headHash 传回 `open()`，
于是接受成功后前端重新打开了旧版本：历史面板写着 `#2 … 5000 ms`，而下方谱面条读
`渲染 5276 ms`，两处自相矛盾——用户会以为「接受」没生效。

修复：`App.tsx::afterDecision(headHash)` 由服务端把决策后真正移动到的 hash 返回给调用方，
`CompareView` 只在拒绝/放弃分支回传 `result.baseHash`（`packages/ui/src/components/CompareView.tsx:79`）。
实测（打包态 `Ossia.app`，Computer Use 真实点击 `接受`）：历史新增 `#3 AI 修改 当前 … 3b8739fa
player 2 页 · 5064 ms`，谱面条同步为 `引擎 2.26.0-darwin-arm64 · 渲染 5064 ms`（等于「修改后」那一侧），
`db.sqlite` 里 `documents.head_hash = 3b8739fa`，旧 `#2` 降为 `5721b534 · 4852 ms` 且不再是 head。

### 3.5b 选中低音谱表后高亮框不绘制（UI 缺陷）

`layout-join.ts::measureGrid` 把同一 system 内声部平行的列折叠成一条记录，`staff` 恒取上谱表
（实测该 MIDI 文档全部列 `staff: 0`）。而 `/locate` 返回的是命中谱表（点低音谱表 → `staff: 1`）。
`ScoreView` 的覆盖层按 `col.staff === staff` 过滤，于是**只有低音谱表的选中画不出框**——
用户点了有反应（文案正确、提交按钮可用）但谱面无高亮。

修复：小节列属于整个 system，覆盖层改为「选中键的谱表存在时高亮该谱表，否则高亮 system 首谱表」，
键为 `staff:measure`。实测（Vite dev + 浏览器真实点击）：`选中：谱表2 第 21 小节` 同时
`rect.sel` 落在 `x=53.03, y=78.678`，即 system 3 的低音谱表位置，与几何一致。

### 3.6 Next standalone `server.js` 绑定 `HOSTNAME || '0.0.0.0'`〔历史：standalone/server.js 交付形态已于 2026-10-10 删除；但「服务端必须显式绑定地址」这条约束对任何部署依然成立，见 §9〕

不设置 `HOSTNAME` 时，排版引擎会监听所有网卡（同一局域网可无 token 访问）。外壳强制
`HOSTNAME=127.0.0.1`（见 `sidecar.rs` 注释）。dev 未设 `OSSIA_TOKEN` 时，服务仍拒绝非
loopback 的 Host 头（实测原始 socket 打 `Host: evil.example` → 403）。

### 3.7 Tauri command 拒绝纯 string 错误 → UI 显示 "undefined"

修复：`packages/ui/src/main.tsx::describe(e)` 统一把未知错误转成一行可读文本。

### 3.8 复制运行时导致 LilyPond 拒绝启动〔历史：`prepare.mjs::replaceTree` 已删除；mtime 规则本身仍由 `scripts/engine.mjs` 在 `vendor/` 安装路径上保证，见 ADR-0001 §4.2〕

LilyPond 首次运行编译 Guile 模块，`.go` 早于 `.scm` 时拒绝启动（实测首次渲染 165 s）。
`prepare.mjs::replaceTree` 用 `cpSync({preserveTimestamps:true})`；`vendor/ENGINE.lock`
另记录 `touch_newer = "*.go"` 供 `scripts/engine.mjs` 处理。

### 3.9 `parseStaves` 只认得 musicxml2ly 的形状（致命，仅 MIDI 导入触发）

谱表 × 声部的join表是定位链路的前提（L2 只看得到线组，说不出「哪条谱表刻的是哪个声部」）。
但 `packages/app/src/server/locate.ts::parseStaves` 原先只解析 musicxml2ly 的
`\new Staff = "P1"` / `\context Voice = "…"` 引用形状，而 midi2ly 写的是另一套：

```ly
\score { << \context Staff=trackB \trackA \context Staff=trackB \trackB >> }
% 声部在文件上方的顶层组里声明
trackB = << \context Voice = voiceA \trackBchannelA … >>
```

即 context 名**不带引号**、同一个标签可以出现两次（两次是**同一条**谱表）、声部藏在顶层
`trackX = << … >>` 组里。实测修复前每个 MIDI 导入的 join 表都是 `[{staff: 0, voices: []}]`，
后果有两处，且都不报错：

1. **任何自然语言修改都失败**：授权行找不到所属 voice → `no-such-locator`
   （实测 job `b250fd04…` → `error no-such-locator`；而同一条 `{voice: "trackBchannelB"}`
   的定位器能成功，说明失败点就在 join 表为空）。
2. **点错谱表**：`voicesForMeasure` 在 join 表为空时退化为「返回全部区域」，于是点低音谱表也报出上谱表的
   声部（两条谱表都拿到 `trackBchannelB`），改到了用户没选的那一行。

修复：按 meaningful-token 流重写解析（`meaningful / labelled / topLevelGroups / groupRefs /
voiceEntry`，加 `referencedVoice(…, unquoted)`），并让未加引号的标签成为谱表身份（同标签两次 = 同一条谱表）。
实测该 MIDI 文档现在是 2 条谱表：`[trackAchannelA, trackBchannelA, trackBchannelB]` /
`[trackAchannelA, trackCchannelA, trackCchannelB]`，会发声的声部按谱表解析；musicxml2ly 的
piano 与 parts 两种形状输出不变（对 `work/samples/` 全部 8 个 `.ly` 逐个核对）。
回归固化为 `packages/app/scripts/verify-locator.ts`（15 项）。

### 3.10 历史行说「未渲染」，同一版本的状态条却报出渲染耗时（UI 自相矛盾）

`open()` 先读 `GET /documents/[id]` 拿到链路快照，再渲染选中版本，但**渲染完仍把渲染前的快照**放进
state。服务端只对「本进程渲染过」的版本给出 `preview`（`peekRendered`），于是刚打开的当前版本
`preview` 为 null，历史行显示 `未渲染`，而紧邻的状态条写着该版本的耗时。
实测（打包态）：`#3 AI 修改 当前 … 3b8739fa player 未渲染` 与 `引擎 2.26.0-darwin-arm64 · 渲染 5123 ms`
同时出现——用户会怀疑谱面看的不是那个版本。

修复：`packages/ui/src/state.ts::withPreview(detail, hash, payload)` 把已渲染的 payload 折回快照，
`App.tsx::open` 用它再 dispatch。实测（dev 浏览器 + 打包态各一次）：
`#4 … 2 页 · 4799 ms` 对上 `渲染 4799 ms`；再点开 `#1` 后，与它内容同 hash 的 `#3` 也一并显示
`2 页 · 4685 ms`（同一份渲染结果，符合 CAS 语义），从未打开过的 `#2` 仍显示 `未渲染`——
没有把「没渲染」伪装成「渲染过」。

## 4. 安全与隔离（G6）实现

| 项 | 实现 | 实测 |
|---|---|---|
| 出口绝对路径脱敏 | `redactPaths` 只保留 basename（3 段以上才算路径） | `81/4` 这类时值分数不被误伤 |
| 服务端不下发源码 | `/versions/[hash]` 只返回几何 + 声部 + 小节范围 | flow 断言响应不含 `\new` |
| 能力清单最小化 | `capabilities/default.json` 不授予 fs / shell / network | webview 只经 IPC 拿 endpoint |
| 引擎优先级 | `OSSIA_LILYPOND_ROOT` → `vendor/` → appdata | 启动日志 `engine ok [vendor] lilypond 2.26.0` |
| API 地址校验 | 壳只接受 `http(s)` origin 的 base（`lib.rs::is_http_origin`），且错误串不回显原值（URL 可能含 `user:***@`） | `cargo test`：`file:///etc/passwd` 被拒且错误信息不含 `passwd` |

**2026-10-10 删除的两行**：「每次启动独立 token」（Rust `getentropy` 生成 per-launch secret）与
「HOME 隔离」（sidecar 的 `HOME` 指向 app data）。两者都是包内 sidecar 的伴生机制，随该形态一起移除。

> ⚠️ **鉴权现状（用户决定：暂不处理）**。`http.ts::authorize` 只剩两种模式——设了 `OSSIA_TOKEN`
> 就校验 `x-ossia-token`；没设就退化为「仅允许 loopback Host」。远端部署若两者都不设，等于
> 所有 API 公开。`store.ts` 的 `documents` 表也还没有 owner 列（无多用户隔离）。
> 桌面壳目前把 token 作为**配置**（`OSSIA_API_TOKEN` / `<app_data>/config.json` 的 `apiToken`），
> 不再生成。这一条是已知的、被明确接受的缺口，见 §6 第 1 项。

## 5. 跨端形态：UI 能否放在 Next.js 侧？（回答用户提问）

结论：**用户的直觉是对的**，UI 必须是平台无关静态 SPA，不能是 Next.js SSR 页面。
桌面端用 `<webview>` 加载远端 URL 做主界面在 iOS 上确实是上架风险。

Tauri 2 侧证据（`v2.tauri.app/start/frontend/`，本会话抓取）：

> Use static site generation (SSG), single-page applications (SPA), or classic multi-page apps (MPA).
> Tauri does not natively support server based alternatives (such as SSR).
> Use a proper client-server relationship between your app and your API's (no hybrid solutions with SSR).

即：Tauri 的移动端做法是把前端**构建产物内嵌进二进制**，由内置协议
（`tauri://localhost` / Windows `http://tauri.localhost`）提供给 webview，而不是远端拉取。
本地直接验证了这一点：SPA 资源文件名 `index-W2-SSYW3.js`、`core-CwxXejkd.js`
能在 `Contents/MacOS/ossia-desktop` 二进制里 `strings` 搜到。

Apple 侧证据（`developer.apple.com/app-store/review/guidelines/`，本会话抓取）：

- **2.5.2**：Apps should be self-contained in their bundles, and may not download, install, or
  execute code which introduces or changes features or functionality of the app.
  → 「下载并执行决定功能的 JS」正落在这一条。
- **4.2.3(i)**：Your app should work on its own without requiring installation of another app to
  function. → 远端 UI 不可用时的最低功能线。
- **4.2.7**：Remote Desktop Clients（镜像特定软件/服务而非通用镜像时）只能连用户自有主机、
  且限本地/LAN 网络。
- **4.7 / 4.7.1+**：未内嵌进二进制的 HTML5/JS 小程序、插件、聊天机器人是**有条件**允许，
  且上架方对其内容负全责（需逐条满足额外规则）。

因此本项目采用的形态（2026-10-10 起，桌面与移动走同一条数据通路）：

| 层 | 桌面（macOS/Windows） | 移动（iOS/Android） |
|---|---|---|
| UI | 静态 SPA 内嵌进二进制（已实现） | 同一份 SPA 内嵌（同一代码库） |
| API | `packages/backend` 部署：本地开发跑 `pnpm dev:api`，正式交付指向远端同一套 API | 远端部署的同一套 API（未实现，见 §6） |
| 排版引擎 | 服务端承载 | 服务端承载（G4：移动端不承载引擎） |

本节关于 UI 的证据链（Tauri 不支持 SSR、Apple 2.5.2 / 4.7）与结论不变：**UI 必须内嵌，远端只给数据**。
被 2026-10-10 的决定替换掉的是「桌面端 = 包内 sidecar」那一格：外壳不再定位运行时、不再 spawn 进程、
不再注入 per-launch secret，只把 API 地址当配置交给 webview。这样做的直接后果：

- `.app` 体积从约 281 MiB 降到 **10.00 MiB**（实测 `tauri build` 输出，见 §7）。
- 硬编码运行时的需求消失：`scripts/runtime.mjs`、`vendor/NODE.lock`、`vendor/node/`（可重定位 Node）
  与 standalone `server.js` 交付链路全部删除；`entitlements.plist` 里的
  `allow-unsigned-executable-memory` / `allow-jit` / `disable-library-validation` 三条豁免一并移除。
- 桌面端失去离线渲染能力：断网即无法渲染。这是产品选择而非技术障碍。
- 「iOS 无法 exec Node」不再是端间差异，因为桌面也不再 exec Node；四端的差异收敛为「连哪个部署」。

## 5b. 打包态真实交互证据（外壳 webview 内真实点击）〔历史：2026-10-09 的包内 sidecar 形态〕

> 以下证据针对**已被 2026-10-10 决定删除的交付形态**（`.app` 内含 `Resources/sidecar` 与
> `Resources/engine`）。它证明的是四条产品链路本身的行为，这部分结论仍然有效；但表中「打包态」
> 这一运行环境已无法用 §7 的命令复现。当前形态的等价验证见 §9 的 dev 桌面通路实测。

以下每一步都在 `Ossia.app` 的 webview 里用真实点击完成（不是 curl，也不是浏览器），因此覆盖的是
真正交付给用户的那份产物。跨两次连续打包（接受那行在修复 3.5c 后的构建上，导出/回退那两行在修复
3.10 后的构建上），所以同一版本在不同行里的耗时会不同——每次启动 sidecar 都要重渲染一遍。

| 链路 | 操作 | 实测结果 |
|---|---|---|
| 点击定位 | 在谱面点三次（低音谱表 m9、第一系统低音谱表、上谱表） | `选中：谱表2 第 9 小节（…VoiceOne）`、`谱表2 第 1 小节`、`谱表1 第 10 小节（PartPbeFivee…VoiceOne）` |
| 自然语言修改 + 5 闸门 | 提交「在 m45 小节开头加入 p 力度记号」 | `✓ G-a … ✓ G-e` 全过；`radius 0 <= 5 note events`；`non-sounding edit: +[\p] -[]`；模型 49766 ms |
| 接受 | 点 `接受` | 历史新增 `#3 AI 修改 当前 … 3b8739fa player 2 页 · 5064 ms`，状态条同步为 `渲染 5064 ms`（= 修改后那一侧），`db.sqlite` 中 `head_hash=3b8739fa` |
| 导出 PDF | 点 `PDF` | `~/Downloads/majo-3b8739fa.pdf`，52190 B，`%PDF-1.4` … `%%EOF` |
| 导出 MIDI | 点 `MIDI` | `~/Downloads/majo-3b8739fa.midi`，4834 B，`MThd` |
| 版本回退 | 点 `#2` 行的 `回退到此版本` | 新增 `#4 回退 当前 … 5721b534 user 2 页 · 5168 ms`；`#3` 保留为历史节点、未删除；状态条 `渲染 5168 ms` |

回退这一行同时验证了 ADR-0001 §6.4 的「回退是追加节点而非倒带」：链变成 `#1 导入 → #2 → #3 → #4 回退`，
`#4` 与 `#2` 内容同 hash（`5721b534`），所以两行都显示同一次渲染的耗时——这是 CAS 的正确表现，
不是重复渲染。

3. **Windows 未验证**：`origins.ts` 已预留 `http(s)://tauri.localhost`，但无实机运行证据。
 4. ~~打包态 webview 内的交互未直接驱动~~ **已结案**（2026-10-09 补测，见 §5b）：
   `app.click([x,y])` 的坐标要按截图的**原生像素空间**给（窗口 2720×1800 @2x，等比缩放后的
   显示坐标需 ×1.406），先前「事件不到达」是坐标落在 webview 之外。

   仍是规范层未结案项，MVP 未实现。
6. **签名/公证为 adhoc**：`Signature=adhoc`（实测 `codesign -dv` 输出 `flags=0x20002(adhoc,linker-signed)`），
   仅供本机运行，分发需 Developer ID + notarization。
7. **测试层为空**（2026-10-10）：原 `verify-*.ts` 五套回归脚本已删除，脚本备份在
   `/tmp/ossia-verify-scripts-1791548501/`；`vite.config.ts` 的 `test` 块目前只有 exclude，
   没有任何 suite。本文 §3 各缺陷的「回归固化为 …」那几处指向的脚本均已不存在。
   现存可运行的验证只有：`pnpm check`（fmt + lint + typeAware）、`pnpm typecheck`、`pnpm test:desktop`。
8. **PDF 不是内容哈希的缓存命中（2026-10-10 注释清理时实测发现）**。`render.ts` 文件头声称
   「产物按其来源内容哈希寻址，重渲染即缓存命中」——这对 SVG 与 MIDI 成立，对 PDF **不成立**：
   Ghostscript 把 CreationDate 与 XMP DocumentID 写进 PDF，所以同一个不可变 `.ly` 每次冷渲染
   都产生新的哈希、新文件、新 `assets` 行。
   实测：`.ossia` 里 8 个版本对应 **16 行 pdf**（每版本 2 次进程重启后渲染）；同一版本连渲两次，
   `svg` / `midi` 新增 0 行（`INSERT OR IGNORE` 生效），`pdf` 新增 2 行。两份 PDF 的差异是 87 个字节，
   全部落在 XMP 时间与 `/ID` 上，30 个 xref 偏移完全一致（即乐谱内容逐字节相同）。
   影响：`.ly` 不变但 PDF 无限累积，且旧 PDF 文件永久成为孤儿（`peekBinary` 只认当前进程内存里
   的那份 ref）。进程内不暴露，重启后必现。
   可选修法：渲染时给 Ghostscript 固定时间戳，或 PDF 导出走「按版本内容哈希现生成」而不入库。
   **MVP 未处理**，需与缓存/GC 策略一起决定。

## 8. 构建副作用（已按 2026-10-10 的决定结案）

### 8.1 源码树里混进了 31 个编译产物 `.js`（其中 `next.config.js` 会**遮蔽** `next.config.ts`）

`packages/{app,ly,ui}` 的每个 `.ts`/`.tsx` 旁边都有一个同名 `.js`（含 `scripts/verify-*.js`），
时间戳全部集中在 18:29，内容是去掉类型标注的转译产物。成因是一次**裸 `tsc <文件>`**：
那种调用不读 `tsconfig.json`，因此 `noEmit: true` 不生效，产物就落在源文件旁边。
已验证 `pnpm typecheck` 与四个 `verify:*` 都不会重新生成它们（清掉后复跑全部脚本，0 复发）。

路由文件这一类是**无害**的：Next 的 `pageExtensions` 默认 `["tsx","ts","jsx","js"]`，
`route.ts` 排在 `route.js` 之前，实测删掉 `.js` 后三个 typecheck + 三套 verify 全绿。

但 `packages/app/next.config.js` 是**有害**的，实测（临时在 `.js` 里加一行日志起 dev 服务）：

```text
OSSIA_PROBE_LOADED next.config.js
✓ Running next.config.js took 53ms
```

即 Next 找配置文件时 `.js` 先命中，`next.config.ts` 完全不参与。两者当前内容等价，所以没造成行为差异，
但以后改 `.ts` 会静默无效——这类「改了没反应」正是最难查的。已把 `.js` 移出源码树，实测现在
`✓ Running next.config.ts took 28ms`。

31 个文件全部备份在 `/tmp/ossia-stray-js-1791544819/`（未删除），确认无误后可直接丢弃。

**决定：不加 `.gitignore` 规则。** 因此这类产物仍可能在有人跑裸 `tsc <文件>` 后重新出现在
`git status` 里（它们与 `.ts` 同名同目录，一眼可辨）。`next.config.js` 那一格是唯一的实质风险，
已排除；提交前若看到 `packages/**/*.js` 与同名 `.ts` 并存，直接删掉 `.js` 即可。

### 9.1 决定与影响面

| 影响 | 内容 |

| 新增 | `src-tauri/src/lib.rs` 的 `get_endpoint`（配置解析）、`packages/desktop/scripts/ui-dev.mjs`（24 行，接替 prepare.mjs 的 SPA 部分）、`packages/backend/.env.development.local` + `.env.production`（两者均 gitignored，见 §9.3） |

| 离线 | 桌面端失去离线渲染：断网即无法出图（产品选择） |

### 9.2 壳的配置模型

`packages/desktop/src-tauri/src/lib.rs` 只剩一个 command，优先级为：

```
OSSIA_API_BASE（env）  →  <app_data>/config.json 的 apiBase  →  http://127.0.0.1:3210
```

- 保留 config 文件这一层的理由：从 Finder 双击启动时没有 shell 可以注入 env，纯 env 方案在实际
  交付中等于只有 loopback 一条路。
- `apiToken` 同样由配置给出（不再由壳生成）。URL 必须过 `is_http_origin`；被拒时错误串只给
  scheme 标签，不回显完整值——base URL 可能含 `user:***@`，而这串字会进 webview。
- Rust 测试 19 → 7 项：sidecar 的 token/port/health/launch 断言随代码删除，新增的 7 项覆盖
  base 规整、空配置回落默认、file 生效、非 http 拒绝且不回显机密、畸形 JSON 报错原因、
  空 config 文件不算错误、camelCase 序列化。env 优先于 file 那一格**未测**（`setenv` 是进程全局，
  与其他并发读取 env 的测试冲突），靠代码审查保证。


### 9.3 数据目录：`OSSIA_DATA_DIR`

`packages/backend/src/server/store.ts::resolveDataDir`（纯函数，可单测）：

| `OSSIA_DATA_DIR` | 结果 |
|---|---|
| 未设，`NODE_ENV=production` | `~/.ossia` |
| 未设，其他 | `<repo root>/.ossia` |
| `~/x` / `~` | 展开到 `os.homedir()` 下（`.env` 文件不是 shell，Node 不会自动展开 `~`） |
| `x` / `./x` | 相对 repo 根解析，使 env 文件不绑机器 |
| `/x` | 原样 |

所有 `.env*` 一律 **gitignored**（`.gitignore` 里就一条 `.env*`，覆盖全部 mode）：env 文件是部署配置，
也是 `OSSIA_MODEL_API_KEY` / `OSSIA_TOKEN` 唯一该待的地方，仓库里不留任何副本。因此下面两个文件只存在于
配置过它们的机器上，**且内容都等于代码默认值**——删掉它们行为不变，新克隆的仓库不需要任何 env 文件就能跑。

- `packages/backend/.env.development.local` → `OSSIA_DATA_DIR=.ossia`（dev 数据留在仓库，
  `rm -rf .ossia` 即重置全部测试文档）。个人覆盖点，密钥写这里。
- `packages/backend/.env.production` → `OSSIA_DATA_DIR=~/.ossia`。本机 prod 覆盖点；真实部署更应
  用进程环境给出，而不是把这个文件搬上服务器。

需要「团队共享的非机密默认」时，正确位置是代码默认（`resolveDataDir` / `agent.ts` 已如此），
不是提交一个 `.env`。

实测（两条都用 throwaway HOME / 独立端口跑，互不污染）：

- dev：`pnpm dev:api` → 首次请求即创建 `<repo>/.ossia/{db.sqlite,cas,assets}`，`/api/v1/documents` 200。
- prod：`next start` 配 `HOME=<tmp>` 且不给 `OSSIA_REPO_ROOT` → 创建 `<tmp>/.ossia/{db.sqlite,cas,assets}`，
  `/api/v1/documents` 200，仓库内没有再出现字面量 `~` 目录。
- 反向验证：改造前的旧构建读到 `~/.ossia` 时会在 `packages/backend/` 下建字面量 `~` 目录

### 9.4 关掉 TypeScript 增量缓存

`packages/backend/tsconfig.json` 原来是全仓唯一开 `"incremental": true` 的配置（`packages/ly`、
`packages/ui` 都是 `noEmit: true` 且不开增量），因此 `tsconfig.tsbuildinfo`（258 KB、
597 个文件指纹）只有它一个生产者。它当时状态是 `??`：**未跟踪也没被忽略**，任何一次 `git add -A`
都会把它扫进索引。

实测（`pnpm exec tsc -p tsconfig.json --noEmit`，同机连续跑）：开增量时「带缓存」0.216s、
删掉缓存冷跑 0.123s；关掉增量后连续两次 0.271s（首次）/ 0.135s（文件系统缓存已热的稳态）。
三个包的 typecheck 合计不到 1s，稳态耗时与增量缓存无关，元数据的读写与校验反而更贵，
所以在这个仓库规模上是净开销。

**决定：删除 `"incremental": true`，并删掉已生成的 `tsconfig.tsbuildinfo`。** 不提交该文件：它与编译器
版本和依赖树绑定，性质同 `next-env.d.ts`。内容本身是干净的（0 条绝对路径、0 处 `$HOME`，路径都是
`../../node_modules/.pnpm/...` 相对形式），所以这不是隐私问题，纯粹是工程约定。

`.gitignore` 仍保留一条 `*.tsbuildinfo` 作为兜底：万一有人跑裸 `tsc --incremental` 或将来重新开启增量，
它不会以 258 KB 的未跟踪产物出现在 `git status` 里。

> `packages/desktop/src-tauri/target/` 下另有 5 份 sidecar 时代构建残留的 `*.tsbuildinfo`，已被 `target/`
> 规则覆盖，随下一次清理自然消失。

对 BMP 内的 `{}` 是安全的，但需要显式放行）。

### 9.5 拍平 `tsconfig.base.json`

根级 `tsconfig.base.json` 曾经定位是「统一全仓 TS 约定」，实测只剩一个消费者：
`rg 'tsconfig.base'` 命中唯一一处 `extends`，即 `packages/ly/tsconfig.json`；`packages/ui` 与
`packages/backend` 各自内联完整 `compilerOptions`，不 extends 任何文件。

`tsc --showConfig` 对比三包生效配置：base 的 15 个键里，除 `types`（ui 用 `vite/client`）外全部被
ui / backend 逐字重写，base **唯一没被复制的键是 `forceConsistentCasingInFileNames`**——TS 5 起这是
默认行为，属于历史遗留。也就是说这个文件统一不了任何东西：明天有人在 ui 里关掉 `strict`，它拦不住；
它只是给 ly 多包了一层间接，还附带一个过时选项。

**决定：内联到 `packages/ly/tsconfig.json` 并删除根文件，不引入新约定。** 内联时去掉
`forceConsistentCasingInFileNames`，其余 13 项 + ly 原有的 `rootDir` / `allowImportingTsExtensions` /
`erasableSyntaxOnly` 合并为一个自解释的配置。没有改成「三包共享真 base」，是因为 backend 与 ui 的分歧
是真实的（Next 需要 `jsx`、DOM lib、`allowJs`，且要覆写 `verbatimModuleSyntax`），那样只会得到一个
人人都要改几项的漏底。

> 附带确认：跨包类型解析不依赖这个文件。`@ossia/ly` 通过 package exports 把 `.` 指向
> `./src/mod.ts`，消费方（`packages/backend/src/server/*.ts` 等）靠该 exports 解析，与根 base 无关。

实测：`pnpm typecheck` 三包全 Done、退出 0；`tsc --showConfig` 的生效选项与内联前逐项一致（含 TS
自动补的 `preserveConstEnums`）。（`pnpm check` 的警告数后来在 §9.6 的清理里从 14 降到 5。）
