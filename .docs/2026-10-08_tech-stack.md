## 1. 背景与目标

Ossia 是跨端（macOS / Windows / iOS / Android）乐谱修订应用：用户导入既有 MIDI/MusicXML 乐谱，
在练习中就谱面问题提交自然语言描述，服务端 Agent 完成修改并回写乐谱，最终导出出版级 PDF 与
MusicXML/MIDI 互换文件。

| ID | 目标 |
|---|---|
| G1 | 一致性：渲染所指、用户所选、Agent 所改、补丁落点必须归一到同一文档模型 |
| G2 | 可审计：所有编辑在服务端以结构化补丁留痕，可 diff、可撤销、可复现 |
| G3 | 模型经济性：进入 LLM 上下文的乐谱表示最小化（单任务窗口 < 5k tokens，长谱按窗口切分） |
| G4 | 移动端可用性：移动端不承载排版引擎；服务端为唯一渲染权威 |
| G5 | 发布兼容：输出无损对接 MusicXML 4.0 生态（mymusic5 / Dorico / MuseScore / Flat） |
| G6 | 面向演奏者：内部表示（补丁、AST、源码）不作为交互界面呈现 |

## 2. 决策概览

| ID | 决策项 | 结论 |
|---|---|---|
| D1 | 客户端形态 | Tauri 2，单一代码库覆盖四端 |
| D2 | 服务端形态 | Node.js 编排 Agent/补丁/渲染/导出；GPL 工具链以独立进程隔离 |
| D3 | 真源格式 | LilyPond 源码（`.ly`）；导入基线 MusicXML 随文档留存 |
| D4 | 排版引擎 | 服务端 GNU LilyPond 官方原生二进制 tarball（非容器、非 WASM），产出 SVG / PDF / 回放 MIDI（§4.2）。注：macOS 验证产物为 darwin-arm64 包，Linux 服务器部署取 linux-x86_64 包 |
| D5 | 引擎交付 | 官方 tarball 安装至固定前缀，与引擎同版本；故障隔离由子进程任务模型承担；交付过程**必须保留文件 mtime**（§4.2） |
| D6 | LLM 交互面 | Agent 读写 `.ly`，经编译日志（`file:line:col`）自检闭环；**校验一律走整曲 MIDI-only 编译 + MIDI diff**，不为自检出图（§8，ADR-0002 §6） |
| D7 | 编辑落地 | `.ly` 前后 AST diff → 结构化补丁 → 校验后应用；补丁同步回放至基线供发布 |
| D8 | MIDI 定位 | 仅用于回放与时间轴对齐，不作为格式转换中间层 |
| D9 | 版本管理 | 服务端线性版本链（数据库 + 内容寻址存储），非 git；`.ly` 与基线不下发客户端 |
| D10 | 交互模型 | 用户提交批注即完成修改请求，界面呈现渲染结果对比，不暴露补丁/AST/源码 |
| D11 | 选择定位 | 三层定位机制（语义索引 + 版面列 + 锚点增强），不以逐符号锚点为唯一依据 |
| D12 | `.ly` 解析器 | 自研 TypeScript parser；语法覆盖范围限定为 musicxml2ly 输出子集（见 §6.5） |
| D13 | 乐器范围 | 产品能力上限跟随 LilyPond 引擎能力；按乐器制式逐层通过 §6.1 一致性校验后开放 |

## 3. 系统架构

```
┌── 客户端（Tauri 2 · macOS / Windows / iOS / Android，Rev.5：不承载服务端）┐
│  谱面浏览 · 批注采集（Apple Pencil / 鼠标）· 选择（音符/小节/符号）      │
│  结果对比视图（变更前/后 + 变化说明）· 历史版本浏览与回退                │
│  本地缓存：SVG / PDF / 版本元数据（不含 .ly 源码与基线）                 │
└──────────────────────────────┬──────────────────────────────────────────┘
                    ① 渲染请求  │  ② SVG + 定位 sidecar + 结果摘要
                                 │  ③ 批注任务（locator 集合 + 自然语言）
┌──────────────────────────────┴──────────────────────────────────────────┐
│  服务端（Node.js）                                                       │
│  A 文档服务  版本链（DB + 内容寻址存储）· 导入基线 · CAS 并发控制        │
│  B 渲染服务  LilyPond 引擎子进程 → SVG / PDF / MIDI                      │
│  C 定位服务  渲染几何 ↔ 源码行区间 ↔ 小节/声部/拍位 三层映射             │
│  D Agent 服务 LLM 读写 .ly · 编译自检 · AST diff → 补丁 · 变更摘要生成    │
│  E 导出服务  补丁回放至基线 → MusicXML(.mxl) / MIDI / PDF                │
└──────────────────────────────────────────────────────────────────────────┘
```

### 3.1 主数据流

1. **导入**：客户端上传 MusicXML/MIDI → 服务端转换得 `.ly` 与基线存档 → 语义校验（§6.1）→ 首次渲染并返回 locator。
2. **浏览与选择**：客户端展示服务端 SVG；选择经 locator 归一为 `{measure, staff, voice?, element?}` 或其区间。
3. **修改请求**：批注文本 + locator 集合提交 Agent → Agent 在 L1 给定的行区间内改写 `.ly` → 五道门校验（行界 / 外区不变 / MIDI-only 编译 / 爆炸半径 / 语义判据，ADR-0002 §6）→ AST diff 生成补丁 → 重新渲染（此处才出 SVG）→ 返回前后谱面与变更说明。
4. **确认与回退**：接受即在版本链推进一个新版本；回退为「指向旧内容的链上新增」并重新渲染。
5. **导出**：PDF 取渲染服务成品；MusicXML/MIDI 由 *基线 + 已接受补丁集* 经 `musicxml-io` 序列化。

### 3.2 真源选择依据

`.ly` 同时是渲染源、编辑源与 Agent 读写面，G1 由结构保证而非依赖同步纪律。量化依据（基准谱：
32 小节钢琴曲，完整数据见附件）：

| 表示 | 体积 | tokens 估算 |
|---|---|---|
| MusicXML 4.0 | 291 KB | ≈ 47,000 |
| `.ly`（musicxml2ly 产物） | 13.8 KB | ≈ 3,500 |

关键属性：指法完整保留（665/665）；行级 token 结构适合精确文本编辑；编译错误携带源码位置，可支撑
Agent 自检；渲染产物自带源码回链（覆盖率与粒度限制见 §6.2，因此不作为唯一机制）。

## 4. 服务端部署

### 4.1 LilyPond 官方分发产物

上游以 GitLab release 提供预编译包（以 2.26.0 为例，2026-10 核对）：

| 平台 | 产物 |
|---|---|
| GNU/Linux x86_64 | `lilypond-2.26.0-linux-x86_64.tar.gz` |
| Windows x86_64 | `lilypond-2.26.0-mingw-x86_64.tar.gz` |
| macOS x86_64 / arm64 | `lilypond-2.26.0-darwin-{x86_64,arm64}.tar.gz` |
| 源码 | tarball |

要点：

- 预编译包含排版引擎、Guile/Scheme 运行时与配套乐谱字体，自足性高。
- **不提供 Linux ARM64 构建，也不提供官方 Docker 镜像**。服务端部署基线定为 **x86_64**；ARM 服务器支持不在当前范围，若未来需要则以自构建为前置条件重新评审。
- `musicxml2ly` / `midi2ly` 位于源码 `scripts/` + `python/`，依赖 Python 3，且**必须与所用引擎同版本
  tag**（跨版本产物会导致语法级失败，附件 §3.2）。
- 替代渠道（PyPI `lilypond` wheel，版本滞后）不作为主渠道。

### 4.2 部署模式：官方二进制直装（不引入容器）

部署单元 = 版本化安装目录 `/opt/lilypond/<tag>/`，其 `bin/` 自带 `lilypond`、`musicxml2ly`、
`midi2ly` 等全部转换器（官方 tarball 实测，附件 §3.12），「同 tag 引擎+转换器」由目录天然保证。

- **版本锁**：渲染任务显式指定 `/opt/lilypond/<tag>/bin/`，tag 记录于文档版本元数据；历史版本
  渲染复现要求对应 tag 目录仍在。
- **故障隔离**：每次渲染为独立子进程（超时 kill、内存 rlimit、工作目录隔离）；引擎崩溃只损失该任务。
- **环境**：macOS 端已验证解压即用；Linux 服务器在目标发行版做一次 glibc/字体冒烟测试（部署核对单）。
- 字体与 Guile 运行时随 tarball 自带，Node 服务不引入系统级依赖。
- **自足性**：包内 `bin/musicxml2ly` 是调用**包内 `libexec/python3.x`** 的 `sh` 包装，部署**无需
  PYTHONPATH**、不依赖系统 Python（附件 §3.13）；`env -i` 空环境渲染正常，安装前缀由构建期注入
  （`etc/relocate/*.reloc`），目录可整体搬迁。
- **交付完整性约束（强制）**：Guile 字节码 `*.go` 位于 `lib/lilypond/<tag>/ccache/`，其新鲜度以 mtime
  与 `share/lilypond/<tag>/scm/**.scm` 比较。**`.scm` 不比 `.go` 新时，引擎每次运行重编译全部 Scheme**：
  tiny 谱实测 **165 s**（正常 0.2 s）；`GUILE_AUTO_COMPILE=0` 无效（退化为解释执行，159 s）。因此：
  - 分发与安装**必须保留 mtime**：允许 `tar -x` / `ditto` / `rsync -t` / `cp -Rp`；**禁止** `cp -R`
    与任何 flatten mtime 的打包步骤（附件 §3.13）。
  - 部署核对单增加冒烟计时：`--svg` 渲染 tiny 谱 ≤ 1 s，超限即判定交付被破坏。
  - 已破坏副本修复：`find <prefix> -name "*.go" -exec touch {} +`（实测 165 s → 1 s）。
  - 该问题属**交付层**，与是否容器化无关，不构成改用容器的理由。

### 4.3 交付拓扑（Rev.5，2026-10-10）

一个部署 = 一份 `packages/backend`（Next.js）+ 一套 §4.2 的引擎安装。客户端只与它的 HTTP API 讲话。

| 端 | 服务端在哪 | 引擎在哪 | 数据目录（`OSSIA_DATA_DIR`） |
|---|---|---|---|
| macOS / Windows | 本地 `pnpm dev:api`（开发）或远端部署（交付） | 随该部署 | dev：仓库根 `.ossia/`；prod：`~/.ossia` |
| iOS / Android | 远端部署（G4：移动端不承载引擎） | 该部署 | 同上（prod） |

约束与代价：

- **桌面端不再有离线渲染**。原方案（把 Node + 128 MB 引擎打进 `.app`，外壳 spawn 并注入 per-launch
  secret）技术上可行且当时已实测跑通，代价是 281 MiB 包体、跨平台可重定位运行时的维护成本，以及与
  移动端两套交付逻辑。Rev.5 认为这些成本大于「断网可用」的收益。
- **鉴权成为全线前置条件**。取消本地 sidecar 后，共享 token / loopback-only 不再是「本机自动成立」的
  假设，任何公网部署都必须先有真实会话鉴权与按用户隔离的存储。**当前未实现**（用户决定：暂不处理），
  缺口记录见 [2026-10-09_mvp-build.md](./2026-10-09_mvp-build.md) §6 第 1 项。
- `packages/backend` 同时是未来的**官网渲染**宿主，因此它的部署形态按「站点 + API」设计，
  而不是按「客户端载荷」设计。


## 5. 版本管理模型（D9）

**决策：线性版本链，不用 git。** git 在本架构中承担的核心价值已被其他决策取代：客户端不持有源码
（D9），无分支合并与三方冲突需求（G6、任务串行化）；diff/回退/CAS 由业务层直接实现更简单。

实现：

- **存储**：`versions(doc_id, seq, content_hash, parent_hash, author, origin, created_at, meta)` 单表链，
  `parent_hash` 构成防篡改前缀链；`.ly` 内容进内容寻址存储（sha256 + zstd），基线 MusicXML 与渲染
  产物同库存放，天然去重。
- **数据库**：**SQLite**（用户决策）。单文档任务串行 + WAL 即满足并发模型，不引入独立数据库服务；
  版本链、补丁审计表、任务队列同库。迁移到 PostgreSQL 仅在出现多写者分片需求时评估。
- **推进**：每个被接受的补丁集 = 一个新版本（`origin = agent | manual | import | restore`）。
  导入新版本（重新上传）作为链上 `import` 节点并携带来源说明。
- **回退**：不删除历史；`restore` 节点指向旧内容哈希，保持链线性、审计完整。
- **并发**：单文档任务串行；写请求携带基版本哈希做 CAS，冲突即拒绝并提示重放任务。
- **diff**：文本 diff（展示用，jsdiff 级别）与 AST diff（补丁用，同一解析器）均可从相邻版本按需计算，
  无需预存。
- **保留策略**：默认全历史保留；提供按文档清理（保留当前版本 + 最近 N 个 `agent` 版本）的用户选项。

git 保留为**导出兼容项**而非内部机制：纯文本真源使「一键导出为 git 仓库」在未来几乎零成本，需要时再加。

## 6. 核心机制规范

### 6.1 导入语义校验

- 转换后以 AST 对齐比较 `.ly` 与基线 MusicXML：小节数、音符事件数、指法数、tie 数必须一致。
- 转换器输出警告（如声部重组 `Negative skip`）时，该文档标记为「需人工确认」，不得静默入库。
- `musicxml2ly` 声明支持 MusicXML 4.0 子集；超出子集的特性在导入报告中显式列为损失项。
- **小节号权威**：`musicxml2ly` 用 `% N` 注释标记每条闭小节线，且会把连续空段压缩为多小节休止
  （`s1*20` 覆盖 20 小节），因此 **`|` 计数不等于小节号**；L1 索引以区间 `[measureStart, measureEnd]`
  建模（规范见 ADR-0002 §3.2）。
- **Negative skip 处理（附件 §3.11）**：该警告意味着时间线压缩/错位而非丢音，不得静默放行。
  导入器将每条警告定位到源事件，导入结果三态：**干净入库 / 声部预处理后重转 / 拒绝并报告**。
  入库判定以 AST diff 精确对齐为准，辅以同协议 MIDI 对齐率参考。
- **乐器范围策略（D13）**：产品不预设「仅钢琴」，能力上限跟随 LilyPond；每种乐器制式以上述校验为
  验收门逐层开放。双乐器最小链路已实测贯通（附件 §3.8）。MVP 范围：**单钢琴谱**（用户决策）。

### 6.2 选择定位（D11）

实测结论：point-and-click 锚点**不足以**独立承担定位职责——整曲 697 音仅产生 508 个锚、去重后落在
49 个源码行；锚的语义是「源码 token 跨度」而非逐音；谱号与结束线不产生锚（附件 §3.6）。
采用三层机制，客户端只与 locator 抽象交互：

| 层 | 机制 | 覆盖 | 依赖 |
|---|---|---|---|
| L1 语义索引（主） | 解析 `.ly` 建立 `measure → 源码行区间`、`staff/voice → 上下文`、`事件序列 → 拍位` | 所有对象，含无锚符号；区间选择（多音/多小节/整谱） | 自研 parser（D12 / §6.5，规范 ADR-0002 §2–3） |
| L2 版面列（辅助） | 从服务端 SVG 提取谱表与段落几何，构建每系统的小节列，点击 `(x,y)` → staff + measure | 点击到小节级、多选起始 | 已结案（ADR-OPEN-3，规范 ADR-0002 §4） |
| L3 锚点增强（可选） | 在小节列内用 `textedit:///…ly:L:C1:C2` 跨度与源码 token 顺序推断具体音符/符号；无锚符号按规则映射（谱表首=谱号/调号/拍号，段末=结束线） | 符号级精度 | LilyPond 开启 `\pointAndClickOn` |

- **locator 规范形式**：`{rev, measure, staff, voice?, element?}`，element 覆盖 `note / chord / rest /
  clef / keySignature / timeSignature / barline / dynamic / textDirection / slur / lyricLine / fingering`；
  选择集支持 `measure` 区间、`beat` 区间与跨元素组合。
- **Agent 侧视图**：向 LLM 提供带行号与小节标尺的 `.ly`，并附本次任务的 `locator → 行区间` 映射表，
  约束其只在给定区间内编辑，越界由补丁应用器拒绝。长谱按任务窗口切分（G3）。
- **视觉模型定位**：不作为主机制。五线谱音符级识图的精度（加线计数、变音记号、声部归属）与可复现性
  不足以保证 patch 落点。仅允许作为 L2 失败时的辅助提示，结论仍须经 L1 语义索引校验后方可使用。

### 6.3 版本与转换约束（强制）

- LilyPond 运行时与 `musicxml2ly` / `midi2ly` 锁定同一版本 tag，同镜像构建。
- 导入固定附加 `--no-stem-directions`：符干由引擎自动规则决定，符合记谱规范并规避已知引擎缺陷（附件 §3.5）。
- `\header` 仅使用 ASCII **仅当启用 WASM 离线渲染时适用**（原生引擎无此限制，附件 §3.12）；
  多语言标题统一以文档元数据承载、由客户端叠加显示，两种引擎路径下行为一致。
- 回放 MIDI 需显式 `\midi` 块，由导入器注入。
- 渲染统一开启 `\pointAndClickOn`，供 L3 使用。

### 6.4 补丁模型与用户反馈（D10）

- 补丁为服务端内部表示：字段含小节号、声部、拍位、操作类型、旧值、新值、影响范围、结果状态；
  用于审计、回退与向基线回放，不作为 UI 元素。
- 用户可见的结果形态：变更前/后谱面（切换或同屏）、变化小节高亮、逐条自然语言变更说明（由 Agent 摘要）、
  接受/撤销操作。失败时返回自然语言原因与受影响范围，不暴露内部错误码或源码。
- 未经应用器校验的 LLM 文本输出不得写盘；补丁应用为事务操作。

### 6.5 `.ly` 解析器（D12）

- 自研 TypeScript parser，随 Agent/定位服务同进程运行，不引入 Python 依赖。
- **语法覆盖 = musicxml2ly 输出子集**，而非全量手写 LilyPond：输入面是机器生成 + Agent 增量修改的
  `.ly`，构造集合可枚举（`\version`、`\header`、`\paper`、`\layout`、变量定义的 `音乐表达式`、
  `<< >>` 与 `\context` 嵌套、`\relative`、词法 token：音高/时值/连音线/tuplet/skip/歌词/Markup 基础式）。
  对超范围构造采取**保留原文不透明段**（verbatim span）策略，保证序列化字节级还原。
- 必备能力：节点携带源码精确区间（行/列）；AST ↔ 文本无损序列化；增量解析（Agent 只改局部时
  仅重析受影响块）；输出 L1 语义索引与 AST diff 供补丁层使用。
- 参照：Lotus 的 jison 语法（约 2000 行，许可未声明，仅可作覆盖范围参考，不可复制）；python-ly
  的解析行为作为差分测试 oracle。验收标准：对基准谱与 musicxml2ly 回归样本，parse→serialize
  字节级恒等，且与引擎编译日志的行号一致。
- **落地状态（Rev.4）**：词法层 L0 与语义索引 L1 已实现并通过验收（语料 `work/samples/`，
  6/6 字节级往返、音乐模式区 RAW = 0、覆盖率 100%、吞吐 1.05–1.11 ms/12 KB），规范移交给
  [ADR-0002](./2026-10-08_ly-parsing-indexing.md) §2–§3；Agent 侧投影与门禁同步结案（§5–§7）。
  **仍未落地**：结构化 AST、AST diff 与补丁回放（依赖 ADR-0002 §9 ADR-OPEN-9 的音高状态机），
  以及增量解析——当前每任务全量重析（12 KB 级 2.21 ms，无需增量）。

## 8. 非功能要求

- **性能（按产物分列，32 小节单钢琴谱实测，附件 §3.13/§3.16）**：原「编译 ≤ 3s」不成立——同一引擎
  同一文件，产出不同耗时相差近 20 倍，故按路径分别设预算：

  | 路径 | 用途 | 实测 | 预算 |
  |---|---|---|---|
  | MIDI-only（`\score` 内去 `\layout`） | 门禁自检（G-c/G-d）、回放数据 | **0.54 s** | ≤ 1 s |
  | PDF | 导出成品 | **1.22 s** | ≤ 2 s |
  | SVG（全曲 3 页） | 谱面显示 | **9.98 s** | ≤ 12 s |
  | tiny（2 小节） | 冒烟 | 0.2–0.5 s | ≤ 1 s（交付完整性检查位） |

  SVG 与 PDF/MIDI 的差距源于字形转路径，**与 `\pointAndClickOn` 无关**（关闭后仍 10.2 s）。
  因此 Agent 校验回环**必须走 MIDI-only 路径**，不得为自检出图（ADR-0002 §6）。
- **导入转换 ≤ 2s**；**locator 构建**：L1 整曲 2.21 ms、L2 单页 4.4–6.3 ms，均可忽略（ADR-0002 §3.3/§4.3）。
- **移动端**：单页 SVG 原始 371–431 KB、**gzip 后 25–28 KB**；4G 首屏 ≤ 2s；不含源码下发。
- **可靠性**：引擎进程崩溃须任务级隔离与重试；补丁与版本推进事务化；历史版本渲染可复现。
- **网络依赖（Rev.5 新增）**：桌面端不再离线可用，渲染请求全部经网络。§8 的按产物预算因此是
  「网络 + 服务端」的端到端预算，而非本机进程预算；SVG 全曲 ≈10 s 这一档在共享部署上还叠加排队。
- **可观测**：每次任务记录输入版本哈希、编译日志、补丁集与耗时，支持全链路复现。
- **可用性**：选择命中在小节级须稳定正确，符号级允许二次确认修正。
